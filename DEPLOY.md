# Deployment

Backend on **Render** (Docker web service + managed Postgres), frontend on
**Vercel**.

## Before you start: the one-instance rule

Calling runs are tracked in an in-process dictionary
(`Backend/services/calling_jobs.py`). A second instance would not see a
campaign started by the first, so an in-flight run would appear to vanish
and its results would never be recorded.

`render.yaml` pins `numInstances: 1`. **Do not raise it**, and do not enable
autoscaling, until that state moves into Postgres or Redis.

For the same reason, avoid Render's **free** plan for the API: free services
sleep after inactivity, which would kill a calling run mid-campaign. The
`starter` plan stays awake.

## 1. Backend — Render

### Deploy

1. Push this repo to GitHub.
2. Render Dashboard → **New** → **Blueprint** → select the repo.
3. Render reads `render.yaml` and creates both the web service and the
   Postgres database, wiring `DATABASE_URL` between them automatically.
4. It will prompt for the secrets marked `sync: false`. Copy these from
   your local `Backend/.env`:

   | Variable | Where it comes from |
   |---|---|
   | `GROQ_API_KEY` | JD parsing, role extraction, call transcription |
   | `APIFY_API_KEY`, `APIFY_USER_ID` | Candidate sourcing |
   | `HUNAR_AI_API_KEY`, `HUNAR_AGENT_ID` | Voice calling |
   | `Enrich_API_KEY` | Email finder + validation |
   | `apollo_io_key` | Contact enrichment (403s on the free plan) |
   | `CORS_ORIGINS` | Set after the frontend deploys — see below |

   `JWT_SECRET` and `JWT_REFRESH_SECRET` are generated by Render; you do not
   supply them.

Migrations run automatically via `preDeployCommand` before the new version
takes traffic. The first migration also creates the `vector`, `citext`,
`pg_trgm` and `pgcrypto` extensions the schema needs.

### Verify

```bash
curl https://hunar-api.onrender.com/health   # {"status":"ok"}
```

### Configure the voice agent (once)

From the service's **Shell** tab in the Render dashboard:

```bash
python -m core.agent_prompt
```

This uploads the screening prompt to `HUNAR_AGENT_ID`. Without it the agent
runs whatever configuration it last had.

## 2. Frontend — Vercel

```bash
cd Frontend
vercel link
vercel env add VITE_API_BASE_URL production
#   value: https://hunar-api.onrender.com
vercel --prod
```

The frontend and backend are on different origins, so `VITE_API_BASE_URL`
must be the backend's absolute URL. MSW is excluded from production builds,
so nothing proxies `/api` on Vercel's side.

### Then close the CORS loop

Set `CORS_ORIGINS` on the Render service to the exact Vercel URL
(`https://your-app.vercel.app`) and redeploy. Until you do, every browser
request fails with an opaque CORS error while `curl` keeps working — a
confusing failure mode worth getting right first time.

## Local development

Unchanged. `Backend/docker-compose.yml` still runs the local Postgres:

```bash
cd Backend && docker compose up -d
uv run alembic upgrade head
uv run uvicorn main:app --reload
```

## Operations

**Logs / shell:** the service's Logs and Shell tabs in the dashboard.

**Deploy an update:** push to the connected branch; Render rebuilds
automatically. Expect brief downtime — one instance, no rolling deploy.

**Backups:** Render's paid Postgres plans include daily backups. Verify the
retention on your plan; the `basic-256mb` tier is small, and a real workload
will outgrow it.

## Known limitations

| Limitation | Impact |
|---|---|
| Single instance, in-process job store | No horizontal scaling. A restart mid-campaign loses tracking of in-flight calls — the calls still happen, but results are not recorded |
| Two hardcoded accounts | No real user management (`Backend/core/auth_config.py`) |
| Every write uses one seeded org | No tenant isolation (`Backend/core/default_tenant.py`) |
| Apollo on the free plan | Returns 403; phone numbers only come from manually added contacts |
| Enrich.so phone lookup | 500 credits per person — skipped unless the balance allows |
| Frontend tests need Node 22+ | `jsdom@30` requires it; the suite cannot run on Node 20 |
